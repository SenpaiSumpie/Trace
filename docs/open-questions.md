| 19 | Interrupted index runs | Resolved for jobs: an index job first fails any build left by a dead attempt, so the revision can be indexed again (ADR-005). | 20 | Chunks of failed snapshots | They are left in place; nothing reads them. | Clean up with the retention policy. |

| 23 | pgvector EF package | `Pgvector.EntityFrameworkCore` 0.3.0 declares EF Core 9 as its dependency; it works with EF Core 10 in all tests here. | Upgrade when a release targeting EF Core 10 exists. |
| 24 | Retrieval baseline | On the fixture's 27 answerable labeled questions (`tests/fixtures/sample-repo.questions.json` version 2, 27 passages), every labeled range is in the top 5 for 24 and in the top 10 for 26. As recall at 10 over labeled locations that is 30 of 31 (development split 15 of 15, held-out 15 of 16). **This measures the plumbing with the bag-of-words fake embeddings on a tiny corpus; it says nothing about quality with a real model.** The three top-5 misses are held-out questions that need semantic matching: `configured-page-size` (not in the top 10), `last-page-ui` (rank 9) and `client-api-key` (rank 8; it was in the top 5 until step M1.3 added files that also talk about API keys). Tests enforce these numbers as regression floors, and require every answerable `dev` question in the top 5. Before step M1.3 the set was 11 questions over 17 passages: 9 in the top 5, 10 in the top 10. | Re-measure with a real embedding provider. |
| 25 | Held-out split | Of the 19 `test` questions, 13 were added in step M1.3 with their labels written before any search was run on them, and have never been used to choose anything. The other 6 are older: after seeing two misses among them I once tried a ranking change (length-normalized `ts_rank_cd`), saw no net effect and reverted it. No retrieval setting was chosen using the `test` split. Running the regression tests shows the held-out numbers to whoever runs them, so the split stays held out only as long as nobody tunes on what they see ([ADR-011](adr/ADR-011-fixture-question-set.md)). | Keep it that way; report the 13 fresh questions separately if the older 6 are ever in doubt. |
| 26 | Tool surface | `search_code` and `read_file_range` are the only tools. They are used by investigations and are not exposed as HTTP endpoints of their own; `find_symbol`, `get_issue`, `list_recent_commits` and `get_commit_diff` are not implemented. | Added by the tasks that need them. |
| 27 | Authorization | Sign in with GitHub; one visibility rule for every endpoint (ADR-002): the public demo fixture for everyone, GitHub repositories only for a signed-in user with access while the installation is active; everything else is a 404. Starting or cancelling work needs sign-in unless `Auth:AllowAnonymousWrites` is true (it is in Development). | — |
| 28 | Citation rules | A citation is valid only if its path exactly equals an indexed path (case-sensitive, no normalization) and its range lies within the file's indexed lines, at most 200 lines. Lines in whitespace-only regions that were not stored are returned as empty. | — |
| 29 | Chat model | Chosen by the owner on 2026-11-20: Anthropic Claude (`Chat:Provider=anthropic`, default model `claude-opus-5-5`, effort `medium`, key in `Chat:ApiKey` or `ANTHROPIC_API_KEY`; `Chat:Model` and `Chat:Effort` override). It uses the official Anthropic .NET SDK. The extractive `deterministic-fake` model remains for tests and local use and is refused in Production. **The Claude adapter has only been tested against canned responses in the documented format, never against the live API.** | Owner supplies a key; run real questions and re-measure the labeled set. |
| 30 | Investigations run on the job queue | `POST /api/v1/investigations` returns 202 with a queued investigation; clients poll `GET /investigations/{id}`. A worker runs it with retries; a killed worker's investigation is restarted by another; `POST /jobs/{id}/cancel` cancels it (ADR-005). No push/streaming of progress: the UI polls every 500 ms. | — |
| 31 | Rate limits and budgets | Requests that start work (`POST /investigations`, `POST .../index-jobs`) are limited per client address (`RateLimits:WritesPerMinute`, default 20; 600 in Development). Model spending fails closed at two levels: 300,000 tokens per investigation (`Chat:MaxTokensPerInvestigation`) and 3,000,000 tokens per 24 hours across everyone (`Chat:DailyTokenBudget`). There are no users, so nothing is per user; behind a proxy every client shares the proxy's address unless forwarded headers are configured. | Per-user limits with authentication; forwarded headers with deployment. |
| 32 | Token usage and cost | Input and output tokens are recorded per investigation (after every model call, across attempts) and returned by the API as `usage`. Tokens are not converted to money in the product: prices change and would be a second thing to keep right. Only the evaluation runner estimates a cost, from prices in its configuration (row 66). Embedding token usage is not recorded. | Add cost reporting if needed. |
| 33 | No confidence value | Results carry `outcome`, `evidence`, `unknowns` and `limitations` but no confidence label: there is no calibrated basis for one. | Revisit once evaluations exist. |
| 34 | Citation validity is not claim validity | A citation is accepted if it is real and was retrieved in the same investigation. Whether the cited lines support the answer is not checked (ADR-007). | Consider a critic pass with a real model. |
| 35 | API surface | Implemented: `GET /repositories`, `POST /repositories/{id}/index-jobs`, `POST /investigations` (`type: question` only), `GET /investigations/{id}`, `GET /investigations/{id}/events`, `GET /jobs/{id}`, `POST /jobs/{id}/cancel`. Not implemented from the handoff table: `/me`, snapshot lists, `/evidence` (evidence is part of the investigation response), issues. No pagination or OpenAPI document yet. | Added by later tasks. |
| 36 | Idempotency | An optional `idempotencyKey` is unique per repository. Repeating a request returns the first investigation; reusing a key for a different question or snapshot is a 409. Requests without a key are never deduplicated. | — |
| 37 | Bad request handling | Malformed JSON bodies return 400 in every environment (`ThrowOnBadRequest` is disabled so Development behaves like Production). | — |
| 38 | UI scope | One page: repository picker, question form, result (answer, evidence listings, unknowns, limitations, steps, provenance). No history of past investigations, no deep link to an investigation, no dashboard, no evaluation view. The result shown is lost on reload (it remains stored and reachable through the API). | Later UI tasks. |
| 39 | Citation links | Evidence shows path, line numbers and commit, but is not a link: the fixture is not hosted on GitHub. | Link to GitHub at the indexed SHA once real repositories are connected. |
| 40 | Fonts | IBM Plex Sans and IBM Plex Mono are bundled from npm (`@fontsource`, SIL Open Font License); nothing is loaded from a third-party host at runtime. | — |
| 41 | Browser coverage | Playwright runs Chromium only, against the Vite dev server with the API in Development mode. No Firefox/WebKit, no production build, no automated accessibility audit; keyboard use of the form is tested. | Widen with the deployment task. |
| 42 | Web API types | `apps/web/src/api.ts` mirrors `Trace.Contracts` by hand; nothing checks they stay in sync except the browser tests. | Generate from an OpenAPI document once one exists. |
| 43 | Job delivery | At-least-once. Handlers must be idempotent; the two that exist are (ADR-005). | Keep true for every new handler. |
| 44 | Worker clocks | Lease and backoff times come from each instance's clock. Instances need synchronized clocks. | Use database time if this ever becomes a problem. |
| 45 | Job defaults | 3 attempts, 30 s lease renewed every 10 s, 10 min per attempt, backoff 5 s doubling to 5 min, 2 concurrent jobs per worker (`Jobs:Concurrency`), 2 s poll. First guesses; only concurrency is configurable. | Tune with real workloads. |
| 46 | Job housekeeping | Finished jobs are kept forever, and there is no list or operator view of failed jobs: a failure is visible on the job, on the investigation, and in the worker log. | Retention and an admin view. |
| 47 | Who may cancel | Any signed-in user with access to a repository can cancel any job on it and see every investigation on it, not only their own. | Per-user ownership if teams ask for it. |
| 48 | Jobs in the API process | `Jobs:ProcessInThisHost` (true in Development) makes the API run jobs itself so one process is enough locally and in browser tests. Production leaves it off and runs `Trace.Worker`. | — |
| 49 | Model-outage retries | A chat model failure is retried up to the job's attempt limit before the investigation fails with `model_error`; each retry restarts the investigation from the beginning. | Revisit cost once a paid model is used. |
| 50 | Model refusals | If Claude declines a request (stop reason `refusal`), the investigation fails with `model_refused` and is not retried. Anthropic's optional server-side fallback to another model is **not** enabled: it is a beta feature whose .NET shapes I could not verify without a key, and a different model answering would make the recorded model ID wrong. Questions about security-sensitive code are the likeliest to be declined. | Decide whether to enable fallbacks once real usage shows how often this happens. |
| 51 | Prompt caching | The Claude adapter asks the API to cache the repeated prefix (system prompt, tools, earlier turns) of each investigation. Whether it actually hits has not been measured. | Check `cache_read_input_tokens` with a real key. |
| 52 | Sending source to providers | With real providers, indexed source text is sent to Voyage (every chunk, at index time) and to Anthropic (retrieved passages, per question). Only the public fixture exists today. | State this in the product before any private repository is connected. |
| 53 | GitHub App not registered | All GitHub code is written and tested against a stub that answers in GitHub's documented formats. **It has never talked to the real GitHub**: the app does not exist until the owner registers it (`docs/github-app-setup.md`). | Owner registers the app and tries sign-in and one index. |
| 54 | Access freshness | Repository access is re-read from GitHub only at sign-in; a session lasts 8 hours. Access removed on GitHub can therefore linger up to 8 hours. Uninstalling, suspending or removing a repository takes effect at once through webhooks. | Shorten the session or re-check per request if needed. |
| 55 | Retention | Uninstalling the app or removing a repository from it deletes the repository and everything indexed from it immediately. | 56 | Sessions | Session cookie encryption keys are stored in the database (`data_protection_keys`), so sessions survive restarts and work across API instances. | 57 | CSRF | Relies on `SameSite=Lax` cookies, JSON-only request bodies and no CORS. No anti-forgery token. `POST /auth/logout` can be triggered cross-site only as a top-level form post, which `Lax` blocks. | Revisit if CORS or form posts are ever added. |
| 58 | Indexing GitHub repositories from the UI | The repository list has an Index / Index again button per repository that queues the job and shows its progress. Progress is lost on a page reload (the job itself continues). Pushes re-index automatically when webhooks are active. | Show running jobs after a reload. |
| 59 | GitHub limits | No handling of GitHub API rate limits beyond failing the job (which is then retried with backoff). Repositories whose file tree GitHub truncates (very large) cannot be indexed. Only the default branch is indexed. | Revisit with real repositories. |
| 60 | Deployment status | Production images and a full local stack built from them are tested (`infra/docker-compose.stack.yml`). **Nothing has been deployed to Azure**: `infra/azure/main.bicep` is only compiled in CI. | 61 | Azure hardening left out | Database reachable from any Azure service (TLS + password) instead of a private network; secrets in the Container Apps secret store instead of Key Vault; no custom domain; no alerts; no deployment pipeline. | Before real users. |
| 62 | Forwarded headers | With `Proxy:TrustForwardedHeaders=true` the API trusts `X-Forwarded-*` from any address. That is only safe because the API has no public ingress; exposing it directly would let callers spoof their address and scheme. | Keep the API internal, or restrict known proxies. |
| 63 | Observability | OpenTelemetry traces and metrics (ADR-008): one trace and one correlation ID follow a question from the request through its job, model calls and tool calls; `X-Correlation-ID` is accepted, generated and returned. Export only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set. **Never sent to a real collector**: verified with in-process listeners in tests only. No dashboards, alerts or latency baselines (P50/P95) yet; database calls are not traced; the web app shows the API's reference with errors but does not start the trace itself. The Azure template does not configure an exporter. | Point at a collector, record baselines, add Npgsql tracing. |
| 64 | Cost of a question | Measured on one 57-file TypeScript repository with `claude-opus-5-5`, two questions, **one run each per version** (model runs vary, so treat as indicative): an answered question fell from about $0.24 to $0.135 and a no-evidence question from about $0.15 to $0.115. Changes: a passage is sent in full once per investigation; only the top 5 hits of a search carry text, the rest are one-line previews the model must read before citing; source is sent unescaped. Prompt caching was already on. The token limits (300,000 per investigation, 3,000,000 per day) count cached tokens at full weight, so they are stricter in dollars than they look. No dollar amounts are stored or shown, only token counts with the cached share. | Repeat over the labeled question set; consider a dollar budget; try search results without text (previews only). |
| 65 | Evaluation runner | `tools/Trace.Evals` runs a dataset's questions through the production `QuestionInvestigator` and writes one result file per run to the git-ignored `eval/results/` (ADR-009). **It has only been run with the fake models on the 11 fixture questions; it has never called Claude or Voyage.** One attempt per question with no retry (the worker retries a model outage); questions run one at a time; only a local directory can be evaluated, not a repository indexed from GitHub. Metrics and comparison of two runs exist (rows 70 to 73); there is no real-model baseline. CI runs a six-question smoke subset with the fake models (row 77). | Step M1.5. |
| 66 | Evaluation cost estimate | Cost is estimated from the tokens the pipeline records and from prices in `Eval:Prices:<model id>` (US dollars per million tokens: input, output, cache read, cache write). Only the fake model is priced (at 0); **no price for a real model is shipped**, and a model without prices gets a `null` cost. The arithmetic is tested against hand-computed numbers, never against a provider's bill. Embedding tokens are neither recorded nor priced, and with a real embedding provider every run indexes the source again. | Owner or step M1.5 adds current prices before a real run; compare one run with the provider's usage page. |
| 67 | Evaluation run database | Each run creates a database `trace_eval_<random>` on the server in `ConnectionStrings:Trace`, and drops it at the end. The configured database is only connected to for `CREATE`/`DROP DATABASE`; nothing in it is read or written. The user needs the right to create databases. A process that is killed leaves its database behind (`docs/evaluation.md` says how to remove it). The production daily token budget applies inside that database, so it caps one run at 3,000,000 tokens unless raised. | Raise `Chat:DailyTokenBudget` for a large real-model run, deliberately. |
| 68 | What a result file records about retrieval | Resolved for recall (ADR-010): from schema version 2 each question carries `retrieval`, the 10 best hits of the production search asked the question itself, as locations without source text. **The searches the model itself makes during an investigation are still recorded with result counts only**, so nothing measures the queries the model writes or which passages it was shown. Result files contain source excerpts and the search queries, and reports contain file paths, so both belong under `eval/local/` for a private repository. | Record the model's own hits if a real-model run shows a gap between retrieval recall and what answers cite. |
| 69 | Dataset labels and revisions | A dataset may name the revision it was labeled against; a run on another revision is refused unless `--allow-revision-mismatch` is given. For a local directory the revision is the content-derived ID of row 16, not a Git commit, so any change to an indexed file changes it. A dataset without a revision is not checked at all. | — |
| 70 | What recall at 10 measures | The retriever, asked the dataset question word for word with a limit of 10 (ADR-010). A labeled location counts as found when a hit in the same file shares at least one line with it, so recall depends on chunk size (40 lines): a large passage finds a small label easily. It is a micro-average over labeled locations. A question whose retrieval could not be made (longer than the 1,000-character query limit, or an embedding failure) is "not measured", not a miss; the report counts them. On the fixture with the fake embeddings it is 10 of 11 (dev 5 of 5, held-out 5 of 6), the same baseline as row 24, and says nothing about a real embedding model. | Re-measure with a real embedding provider (step M1.5). |
| 71 | Citation validity as computed | Validated evidence divided by evidence plus citations the pipeline discarded. "Valid" is the pipeline's own rule (in the snapshot, retrieved in the same investigation, not blank), which is stricter than the handoff's wording. It does not check that the cited lines support the claim. It can read slightly low: when the model reports insufficient evidence but cites anyway, discarded citations are counted and acceptable ones are not recorded. With the fake chat model it was 100% on the fixture (33 of 33), which says nothing about a real model. | A judge or a human review for "supports the claim" is not planned in M1. |
| 72 | Abstention metrics | Precision is correct abstentions over all `insufficient_evidence` results; recall is correct abstentions over unanswerable questions that ran to an end, so a failed unanswerable question counts against recall. Cancelled and never-run questions are left out. The fixture has 7 unanswerable questions (3 development, 4 held-out). **With the fake chat model abstention recall is 0 of 7 and precision is `n/a`**: that model cites whatever its search returns and abstains only when the search returns nothing. Nothing is known yet about how a real model does on them. | Real-model run (step M1.5). |
| 73 | Comparing two runs | `compare` matches questions by ID and calls a question regressed when it lost the outcome its label calls for, a labeled location dropped out of the top 10, its evidence stopped overlapping a labeled location, or a smaller share of its citations was valid. Cost and time are shown but never decide: time varies between identical runs. It does not compare answer text, and one run per side cannot tell a real change from run-to-run variation of a real model. It exits 0 on regressions, and by decision (ADR-012) CI does not gate on it: the build gate is the absolute smoke check of row 77. It has only been used on fake-model runs and hand-built files. | Repeat runs before trusting a small difference. |
| 74 | "Answers citing a labeled location" | An extra number, not a handoff metric: the share of answerable questions whose validated evidence overlaps a labeled location. It is the only signal about answer correctness that needs no judge, and it is weak: an answer can cite the right lines and still be wrong, or be right from other lines. Factual grounding as the handoff defines it is not measured. | Decide on a judged metric after the first real-model run. |
| 75 | Fixture question set | Version 2: 34 questions (27 answerable with 31 labeled locations, 7 unanswerable; 15 development, 19 held-out) over a fixture of 21 files and 27 passages ([ADR-011](adr/ADR-011-fixture-question-set.md)). Every new question and label was written from the source before any search ran on it, and none was changed afterwards. One person wrote the questions, the labels and the fixture content they are about, with no second reader, and several questions share a distinctive word with the lines they are labeled with ("webhook", "rate limit", "stuck worker"), so the set is probably easier for word matching than a stranger's questions would be. 34 questions is small: one question is about 3 points of a split's percentage. Recall at 10 over 27 passages is easy by construction. | A set for a real repository (later M1 step); a second person reviewing labels would help. |
| 76 | "Unanswerable" is a labeler's judgment | A question is labeled unanswerable when the fixture holds no fact that settles it (region, license, .NET version, CI system, latency target, on-call contact, password hashing); each was checked by searching the fixture for the terms an answer would use. A real model may still give a reasonable reply such as "the repository has no users or passwords", which the metrics count as a missed abstention. Questions of that kind were mostly avoided; `password-hashing` is the closest to one. | Look at each unanswerable question's result by hand after the first real-model run. |
| 77 | Evaluation smoke check in CI | The `eval-smoke` job runs six development questions of the fixture with the fake providers and fails the build when `check` finds an expectation of `tests/fixtures/sample-repo.smoke.json` unmet ([ADR-012](adr/ADR-012-evaluation-smoke-check.md)); the result file and report are uploaded as an artifact kept for 30 days. **It guards the plumbing only.** The expectations are today's fake-model behaviour (answered, every label retrieved and cited, no discarded citation), written after looking at a development-split run. Nothing about answer quality or a real model is checked, and abstention is not checked at all: no fixture question makes the fake chat model abstain, so the one unanswerable question in the subset has no expected outcome. The check is absolute, so a number can get worse without failing it, and no build fails on a regression between two runs. A deliberate change to search, chunking or the fake models can break an expectation and then needs the file updated. A run limited by an expectations file records `split` as `subset`; the result format stayed version 2 because no field changed. | Revisit what gates a build once a real-model baseline exists (step M1.5); the owner may want the `eval-smoke` job as a required check if branch protection is turned on. |
