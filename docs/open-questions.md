| 65 | Evaluation runner | `tools/Trace.Evals` runs a dataset's questions through the production `QuestionInvestigator` and writes one result file per run to the git-ignored `eval/results/` (ADR-009). | 66 | Evaluation cost estimate | Cost is estimated from the tokens the pipeline records and from prices in `Eval:Prices:<model id>` (US dollars per million tokens: input, output, cache read, cache write). The fake model is priced at 0 and `claude-opus-5-5` at input 4, output 20, cache read 0.4, cache write 5. **Those four figures were given by the owner from an earlier session and are not confirmed against the provider's price page or a bill**; every estimate in the baseline (row 78) rests on them. | 67 | Evaluation run database | Each run creates a database `trace_eval_<random>` on the server in `ConnectionStrings:Trace`, and drops it at the end. | 68 | What a result file records about retrieval | Resolved for recall (ADR-010): from schema version 2 each question carries `retrieval`, the 10 best hits of the production search asked the question itself, as locations without source text. **The searches the model itself makes during an investigation are still recorded with result counts only**, so nothing measures the queries the model writes or which passages it was shown. | 69 | Dataset labels and revisions | A dataset may name the revision it was labeled against; a run on another revision is refused unless `--allow-revision-mismatch` is given. | 70 | What recall at 10 measures | The retriever, asked the dataset question word for word with a limit of 10 (ADR-010). A labeled location counts as found when a hit in the same file shares at least one line with it, so recall depends on chunk size (40 lines): a large passage finds a small label easily. It is a micro-average over labeled locations. A question whose retrieval could not be made (longer than the 1,000-character query limit, or an embedding failure) is "not measured", not a miss; the report counts them. On the fixture with the fake embeddings it is 10 of 11 (dev 5 of 5, held-out 5 of 6), the same baseline as row 24, and says nothing about a real embedding model. With Voyage on version 2 of the set it is 31 of 31 (row 78), 27 of them at rank 1 or 2; with 27 passages in the index the 10 best hits are over a third of it, so the percentage is close to guaranteed. | Measure on a real repository, where 10 hits are a small share of the index. |
| 71 | Citation validity as computed | Validated evidence divided by evidence plus citations the pipeline discarded. "Valid" is the pipeline's own rule (in the snapshot, retrieved in the same investigation, not blank), which is stricter than the handoff's wording. It does not check that the cited lines support the claim. It can read slightly low: when the model reports insufficient evidence but cites anyway, discarded citations are counted and acceptable ones are not recorded. With the fake chat model it was 100% on the fixture (33 of 33), which says nothing about a real model. With Claude it was 130 of 130 in the baseline run (row 78): the model cited nothing it had not been shown. | A judge or a human review for "supports the claim" is not planned in M1. |
| 72 | Abstention metrics | Precision is correct abstentions over all `insufficient_evidence` results; recall is correct abstentions over unanswerable questions that ran to an end, so a failed unanswerable question counts against recall. Cancelled and never-run questions are left out. The fixture has 7 unanswerable questions (3 development, 4 held-out). **With the fake chat model abstention recall is 0 of 7 and precision is `n/a`**: that model cites whatever its search returns and abstains only when the search returns nothing. With Claude in the baseline run (row 78) precision was 6 of 6 and recall 6 of 7; the miss is `password-hashing` (row 76). One run of seven questions. | More unanswerable questions, on a real repository. |
| 73 | Comparing two runs | `compare` matches questions by ID and calls a question regressed when it lost the outcome its label calls for, a labeled location dropped out of the top 10, its evidence stopped overlapping a labeled location, or a smaller share of its citations was valid. Cost and time are shown but never decide: time varies between identical runs. It does not compare answer text, and one run per side cannot tell a real change from run-to-run variation of a real model. It exits 0 on regressions, and by decision (ADR-012) CI does not gate on it: the build gate is the absolute smoke check of row 77. It has only been used on fake-model runs and hand-built files. | Repeat runs before trusting a small difference. |
| 74 | "Answers citing a labeled location" | An extra number, not a handoff metric: the share of answerable questions whose validated evidence overlaps a labeled location. It is the only signal about answer correctness that needs no judge, and it is weak: an answer can cite the right lines and still be wrong, or be right from other lines. Factual grounding as the handoff defines it is not measured. | Decide on a judged metric after the first real-model run. |
| 75 | Fixture question set | Version 2: 34 questions (27 answerable with 31 labeled locations, 7 unanswerable; 15 development, 19 held-out) over a fixture of 21 files and 27 passages ([ADR-011](adr/ADR-011-fixture-question-set.md)). Every new question and label was written from the source before any search ran on it, and none was changed afterwards. One person wrote the questions, the labels and the fixture content they are about, with no second reader, and several questions share a distinctive word with the lines they are labeled with ("webhook", "rate limit", "stuck worker"), so the set is probably easier for word matching than a stranger's questions would be. 34 questions is small: one question is about 3 points of a split's percentage. Recall at 10 over 27 passages is easy by construction. | A set for a real repository (later M1 step); a second person reviewing labels would help. |
| 76 | "Unanswerable" is a labeler's judgment | A question is labeled unanswerable when the fixture holds no fact that settles it (region, license, .NET version, CI system, latency target, on-call contact, password hashing); each was checked by searching the fixture for the terms an answer would use. A real model may still give a reasonable reply such as "the repository has no users or passwords", which the metrics count as a missed abstention. Questions of that kind were mostly avoided; `password-hashing` is the closest to one. **That is what happened in the baseline run** (row 78): Claude declined the other six and answered `password-hashing` with "there is no password hashing: no users or passwords, one shared API key", which is true and was counted as a missed abstention. The label was left as it is. | Decide whether `password-hashing` is relabeled, reworded or dropped; that changes `datasetVersion`, so do it together with other dataset changes and not to improve a number. |
| 77 | Evaluation smoke check in CI | The `eval-smoke` job runs six development questions of the fixture with the fake providers and fails the build when `check` finds an expectation of `tests/fixtures/sample-repo.smoke.json` unmet ([ADR-012](adr/ADR-012-evaluation-smoke-check.md)); the result file and report are uploaded as an artifact kept for 30 days. **It guards the plumbing only.** The expectations are today's fake-model behaviour (answered, every label retrieved and cited, no discarded citation), written after looking at a development-split run. Nothing about answer quality or a real model is checked, and abstention is not checked at all: no fixture question makes the fake chat model abstain, so the one unanswerable question in the subset has no expected outcome. The check is absolute, so a number can get worse without failing it, and no build fails on a regression between two runs. A deliberate change to search, chunking or the fake models can break an expectation and then needs the file updated. A run limited by an expectations file records `split` as `subset`; the result format stayed version 2 because no field changed. | Revisit what gates a build now that a real-model baseline exists (row 78); the owner may want the `eval-smoke` job as a required check if branch protection is turned on. |
